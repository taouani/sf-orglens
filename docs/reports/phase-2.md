- **Q3 changed.** The test org handed out the draft of a flow, not its active version. You chose on 23 November 2026
  that the active version is fetched by its number and analysed, and a newer one noted (record 0060, which replaces
  0057). The six days of work package 3 did not hold that.
- **Two more objects of the Tooling API.** To compare the rows of flows, a snapshot asks `FlowDefinition` for the
  active and the latest version of each flow (record 0067), and `Flow` for every version (record 0078). You chose
  both on cards, on 23 and 25 November 2026. The plan named only `MetadataComponentDependency`.
- **The corrections of your run were built inside the phase,** six of them before work package 6 was finished: seven
  pull requests and five decision records (0069 to 0072 and 0075) that the plan did not have.
- **Work package 7 does not take the prefix in a name.** A component is of a package where the org lists it as one.
  The org states the package of every component it lists, and a name can carry the prefix of another component it
  belongs to, as a tab carries the name of its object (record 0076).
- **Work package 8 reads more than the plan says:** the fields the layout of a quick action shows, the flow,
  component or page it opens, and the letterhead and documents of a template (record 0077). The status in the plan
  names the first two.
- **Pull requests.** The plan expected about ten. 34 were merged before the close.
- **Effort.** The plan estimated about 27 developer-days. The phase was built in three calendar days, from your
  approval on 22 November 2026 to the merge of work package 9 on 25 November 2026. As in the phases before, the
  estimate measured the size of the work and not the time it took.

## What is not done, and what is not verified

- **The corrections from your run on that org or on any org of that size:** the reading of the Dependency API below
  the limit, the overrides of actions, person accounts, documents, folders inside folders, the lines of the report,
  and the components of managed packages. The test org has no package, no person accounts, no document and no
  folder inside a folder.
- **The Dependency API on an org of yours with the analysis of this phase.** The test org holds 7 flows. Whether the
  analysis misses a pair from flows that neither of us wrote is part H of the test plan.
- An org with many flows, an org with a namespace of its own, a sandbox, another edition than Developer Edition.
- The forms of the Lightning and the Visualforce email templates on an org. Whether the Dependency API reports an
  override by a Visualforce page, an s-control or a Lightning component: it reported the Lightning page on your org.
- **A name alone of a flow, in a snapshot of an org.** The org lists a definition of every flow under the same name
  (`FlowDefinition`), so `orglens impact Invoice_After_Save` ends with `COMPONENT_AMBIGUOUS` and the exit code `2`,
  and the hint names the key to use, `Flow:invoice_after_save`. A name with the element, such as
  `Invoice_After_Save.Update_Account`, works. Not corrected in this phase. The release notes say it.
- The seven missed names, the token of PMM, and the warning for `Id` at the end of a path (10 of the 24 paths not
  followed in PMM end at `Id`): yours to decide.
- [Issue 86](https://github.com/taouani/sf-orglens/issues/86): two older ways the analysis drops a name without a
  warning, found by a review of this phase. [Issue 79](https://github.com/taouani/sf-orglens/issues/79): the number of
  queries of the cross-check where many types are near the limit.
  [Issue 49](https://github.com/taouani/sf-orglens/issues/49) from Phase 1 is open too.
- Whether the time of a snapshot of an org grows with flows: the active version of a flow with a draft costs one
  more retrieve, and the versions of the flows two more queries.
- Memory, in every measurement. Windows and macOS, in every measurement: CI runs the tests there.
- No person has read an entry of the key or of the check by hand.
- Apex, Lightning components, Visualforce, layouts, Lightning pages, reports and permissions are not analysed.
  Approval processes, assignment, escalation and auto-response rules, sharing rules, and duplicate and matching rules
  neither: an answer names them as not analysed where they can refer to it.
- `orglens --help` of `0.1.0-next.2` says that an answer covers objects, fields, validation rules and flows, and not
  the other types of this phase. The text is corrected on `main` and ships with the next version.
