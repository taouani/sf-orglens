# Decision records

A decision record is one short file that states a decision, why it was made, and what it rules out. A change to
the architecture, the data model, the storage format, a public contract or the scope of a release needs one.
[0001](0001-record-decisions.md) describes the practice.

Records 0002 to 0022 write out the 27 decisions the project started from. Those decisions were agreed on 2026-11-11 and
are summarised in the decision log of the [re-architecture plan](../plans/re-architecture-plan.md#decision-log). The
"Decisions" column gives the plan ids each record covers. Record 0001 and the records from 0023 on are decisions made
during the build, with one exception: record 0034 replaces 0008 and covers plan decision A4, which was changed on
2026-11-12. Record 0018 was completed on 2026-11-13 with the parser the maintainer chose. Records 0035 to 0037 are not
decisions of the build either: they hold what the maintainer answered to the Phase 1 plan on 2026-11-15. Record 0038 holds the change the maintainer made when approving that plan on the same day, and supersedes 0036. Record 0039 holds the answer to question Q8 of that plan, and was written with the reader it is about. Record 0040 holds the tables that work package 3 of that plan asks for, with the choices the author made in them. Record 0041 holds the first analysis, which work package 4 of that plan asks for, with the choices the author made in it. Record 0042 holds the reading of formulas, which work package 5 asks for, with the choices the author made in it, and changes one point of 0041. Record 0043 holds how a snapshot is analysed and shown, which work package 6 asks for, with the choices the author made in it, adds the command `analyse` to the set of 0016, and closes the open point of 0032 about the project a Git source is read with. Record 0044 holds the impact answer, which work package 7 asks for, with the choices the author made in it. One of them departs from a sentence of that plan: a result holds one reference and not its whole chain. Record 0045 holds the cross-check with the Dependency API, which work package 8 asks for and record 0034 decided, with the choices the author made in it. Three of them depart from that plan: the rows are kept beside the snapshot and are no references, an end of a row is matched by the id the org listed, and a query at the limit is also asked per group of components. The maintainer answered two questions of it on 2026-11-16. Record 0046 builds what record 0038 decided, in work package 9, with the choices the author made in it: the 21 names of the logic tier, and which tier a failure counts against. Record 0047 holds two corrections made after the first run of the test org with that judgement. Record 0048 holds the key of `orglens.toml` that leaves types out of a snapshot of an org, which that plan proposes and record 0038 left undecided, with the choices the author made in it. The maintainer chose to keep the key on 2026-11-17. Record 0049 holds one more correction, made after the second run of the test org with that judgement. Record 0050 builds the pre-release the maintainer chose with question Q6 of that plan, with the choices the author made in it: where it is, how it is installed, how it is versioned and which workflow makes it. Record 0051 holds what the maintainer answered on 2026-11-17 to the question that plan left open: the first release, from which records 0022 and 0027 fix the names and the JSON contract, is the first one on npm, and no pre-release on GitHub. Record 0052 holds what the maintainer answered on the same day to a finding of the review of record 0050: the project holds its names on npm with empty packages before the first pre-release is published, with the choices the author made in building it. It was never accepted: its own review found that the policy of npm forbids a package that only reserves a name, and the choice went back to the maintainer. Record 0053 holds what the maintainer then chose, on the same day, and supersedes 0052: the pre-release itself is published on npm under the tag `next`, by a workflow in an environment of GitHub that waits for the maintainer's approval, with the trusted publishing of npm. It changes the answer to the sixth question of that plan, and where record 0050 puts a pre-release and how it is installed. It also holds what the maintainer answered when asked again what such a pre-release fixes of the names and the JSON contract: nothing, and the first release of record 0051 is the first version on npm without a pre-release part. Also on 2026-11-17 the maintainer confirmed a rule of record 0046 that the test org had put in question: a component of the logic tier that the org lists and Salesforce does not hand out stays an error, and the snapshot partial. No record changes with that answer. Record 0054 holds what the maintainer chose after the first publish, on the same day: a second pre-release, `0.1.0-next.1`, that changes nothing in what OrgLens does, is published within two days, to try the trusted publishing of npm before the trusted publishers of the two packages expire. Records 0055 to 0058 hold what the maintainer answered to four of the six questions of the Phase 2 plan on 2026-11-22, when approving it.

## Writing a record

1. Copy [0000-template.md](0000-template.md) to the next free number.
2. Keep it short. Link to the plan or research note that holds the detail.
3. Add a row to the table above.
4. Run `pnpm run check:adr`. It checks the format of every record, the links to files, this index, and that every
   decision id in the decision log of the plan is listed by exactly one record in force. It cannot check that the
   text of a record matches the decisions it lists. That is for review.

An accepted record is not rewritten when the decision changes. Write a new record that lists the plan ids it takes
over. In the old record, change only the status line, to `Superseded by [NNNN](NNNN-title.md)`, and change its row in
the table to match. A superseded record keeps its "Decisions" line and no longer counts as covering those ids.
