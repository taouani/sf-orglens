# apex-analysis

## Summary
None of the three candidates gives method -> sObject-field read/write references out of the box; whichever is chosen, the scope/type resolver has to be written in this project. (A) @apexdevtools/apex-parser 5.3.0 and (B) tree-sitter-sfapex 3.0.2 are syntax-only parsers: both parse inline SOQL into a tree, give line/column positions and recover from simple syntax errors, and both have a zero-native-build route on Node 22 (A is pure JS; B via the separate web-tree-sitter-sfapex WASM package, because the native package ships no Linux prebuild and compiled with gcc here). (C) @apexdevtools/apex-ls on npm is not the semantic analyser: version 6.0.2 (Nov 2025, a year stale) is a 648 KB Scala.js bundle exposing only Workspaces.get(dir).findType(name); the real analyser is JVM-only (Maven 6.4.0, 2026-10-22, 29 MB of jars). Run on the JVM, apex-ls gives a resolved method -> method call graph and method -> Apex-field dependencies, but sObject usage only at object level (Schema.Account), with no field names, no read/write flag and no per-reference positions; its position-based getDefinition did resolve custom sObject fields in expressions (16 of 43 labelled references in my corpus, about 6.5 ms per call) but not standard fields, inline SOQL fields or dynamic get/put. On a public 320k-line codebase (NPSP, 1,070 files): A parsed in 18.5 s, B in 2.2-2.3 s, apex-ls JVM loaded in about 15.8 s with roughly 1.1-1.2 GB peak RSS and needed sfdx-project.json, -meta.xml files and all sObject metadata present. A 79-line resolver spike I wrote on B (WASM) scored 41/43 on my own hand-labelled key, which shows feasibility only: I wrote both the corpus and the key. An official Salesforce TypeScript language server exists (forcedotcom/apex-language-support, built on apex-parser 5.2.0) but its README says 'experimental - DO NOT USE' and its packages are not on npm, so it is not a candidate (D). Preliminary ranking: A slightly ahead of B as the syntax foundation, apex-ls JVM as an optional dev/CI oracle only, apex-ls npm unusable. The Tooling API SymbolTable and Dependency API cross-checks could not be exercised (no org access in this session) and their exact shape is unverified.

## Recommendation
Plan Phase 0 on the assumption that the project owns the semantic layer (scopes, declared-type resolution against the snapshot's object/field schema, read/write classification, SOQL field extraction, constant folding for dynamic names), and use the trial to choose only the syntax provider underneath it. Drop the npm @apexdevtools/apex-ls as a candidate (it cannot answer any trial question) and re-scope apex-ls to 'JVM oracle for development and CI': it is the best available independent check of the call graph and of expression type resolution, but it must never be a runtime dependency of the CLI.

TRIAL DESIGN
Corpus, three tiers:
1. Fixture v0 (labelled): the Phase 0 fixture SFDX project, about 12-15 classes and 2 triggers (600-900 lines), 3 custom objects, about 15 custom fields, with a hand-written key expected/apex-field-refs.json of at least 150 tuples (file, enclosing method signature, object, field, R/W/RW, line, category, must|may). Categories: direct read; direct write; compound assignment and ++; multi-hop __r traversal; inline SOQL select/where/order/group/subquery/TYPEOF/parent path; SOQL-typed loop variable, list index and Map.get generic; sObject constructor named args; SObjectField tokens (Account.F__c, Schema.Account.fields.F__c); get/put with literal; get/put with static final constant in same and other class; dynamic SOQL concatenation with known and unknown object; Trigger.new/old/oldMap; inner class; cast and safe navigation; method-return chain; custom setting getInstance(); standard fields; namespaced fields; DML with external-id field; a file with a syntax error; negative controls (field name in comment or label string, Apex property named like a field, local variable shadowing an object name, same field name on two objects).
2. Public code (unlabelled): apex-recipes at commit 5d31e01 (142 files, 17.9k lines) for a 100-reference hand-checked precision sample; NPSP at commit f5072b4 (1,070 files, 320k lines) for robustness and performance.
3. The real org retrieved in Phase 0: robustness, runtime and the Tooling API cross-checks.

Questions each candidate must answer: Q1 per method (including constructors, accessors, init blocks, inner classes, trigger body) the list of (object, field, R/W, line, column); Q2 per inline SOQL the FROM object and every field with clause and relationship path; Q3 dynamic references reported with unknown object and a low-confidence flag; Q4 resolved method -> method edges including trigger -> handler; Q5 class/trigger -> object edges from trigger header, DML and SOQL; Q6 on a broken file, do references outside the broken statement survive and are errors positioned; Q7 clean install on ubuntu/macos/windows with Node 22 and 24, no compiler and no JVM; Q8 throughput and peak RSS on NPSP and the real org.

Metrics and bars: M1 recall on 'must' references >= 95% (exact object, field, method, access, line); M2 precision >= 98% and zero false positives on negative controls; M3 read/write accuracy >= 99% of matched; M4 'may' references >= 80% reported and never as high confidence; M5 >= 95 of 100 sampled apex-recipes references correct; M6 of sObject-field members listed in Tooling SymbolTable.externalReferences for fixture and real-org classes, >= 95% found at class level, every difference triaged; M7 of ApexClass -> CustomField rows in MetadataComponentDependency, >= 95% covered; M8 method -> method edge recall >= 90% against apex-ls JVM summary 'dependents'; M9 zero crashes and >= 99.5% of files yield a usable tree; M10 NPSP parse plus extract <= 60 s and <= 1.5 GB peak RSS in one process; M11 npm ci --ignore-scripts green on the 3x2 CI matrix; M12 hours spent and lines of adapter code per candidate, recorded.

Method: write the resolver once against a thin syntax-adapter interface, with two adapters (apex-parser 5.3.0 pinned exactly; web-tree-sitter-sfapex 3.0.2). Score both with one harness. Run apex-ls 6.4.0 JVM only as an oracle (summaries JSON plus getDefinition at each reported position).

Time-box: 4 working days, hard stop at 5 (0.5 fixture Apex + key + scorer; 1.0 resolver on adapter A; 0.5-1.0 adapter B; 0.5 apex-ls oracle harness; 0.5 Tooling cross-check on the real org; 0.5 decision record with the numbers).

Decision rule: gates first (M11, M9, M10, licence BSD/MIT). Among candidates passing the gates, require M1-M3. If both pass (likely, since the resolver is shared), tie-break in this order: error-recovery result on the broken corpus (Q6), grammar currency (release within 6 months and newest API-version syntax parses), typed API ergonomics in TypeScript, then speed. apex-ls becomes more than an oracle only if both A and B stay under 85% M1 and a hybrid reaches the bar, and then only as an optional Java-requiring deep mode.

Fallback if none reaches the bar: ship with two confidence tiers ('resolved' where the declared type is known, 'name-match' where a field name is matched against the schema), fill class-level recall for org sources from SymbolTable and MetadataComponentDependency (no method, no read/write, no line), state the reduced precision for repo-only sources, and revisit forcedotcom/apex-language-support if it is published.

Preliminary ranking from what was verified: 1) apex-parser (pure JS everywhere, kept more structure on the one heavy broken-code case, distinguishes class/trigger/anonymous units, same grammar that apex-ls JVM and Salesforce's experimental server build on, so oracle disagreements are not parse disagreements); cost is 8x slower parsing, higher memory and tree-shape changes in minor releases. 2) tree-sitter-sfapex via WASM (8x faster, 6.5 MB, my spike was built on it); risks are a single maintainer with a 14-month release gap, coarser recovery on heavy breakage, and a string-typed node API. The gap between 1 and 2 is small and the trial should be allowed to reverse it. 3) apex-ls JVM as oracle only. 4) apex-ls npm: not usable.

## Risks
- The 41/43 spike result is on a corpus and key written by the same author as the resolver; real code (generics, inheritance, method-return chains, properties, namespaces) will be harder and the 95% bar may take more than the time-box
- apex-parser ships tree-shape breaking changes in minor releases (stated in its changelog); an unpinned upgrade can silently change extraction
- apex-parser is about 8x slower and reached about 1 GB RSS on 320k lines when unconstrained; a very large org may need worker threads or per-file caching by content hash
- tree-sitter-sfapex has one maintainer and had a 14-month release gap; its native package has no Linux prebuild, so only the WASM package is safe for cross-platform installs
- tree-sitter accepted non-class content without error and collapsed a heavily broken region into ERROR nodes; silent under-reporting is possible on bad input
- apex-ls JVM reports false errors on valid code (19 on apex-recipes) and thousands of 'Missing' issues when managed-package metadata is absent, so it is an imperfect oracle and disagreements need manual triage
- Standard fields and child relationship names are not present in source-format metadata; without describe data or a bundled standard schema the resolver cannot fully resolve them for repo-only sources
- Dynamic references (get/put with computed names, dynamic SOQL with unknown object) cannot be resolved exactly by any candidate; they must be reported as low confidence or impact answers will look more certain than they are
- The Tooling API cross-check design rests on unverified assumptions about what SymbolTable and MetadataComponentDependency return; if sObject fields are not listed there, M6/M7 must be redefined
- Managed-package Apex bodies are hidden in orgs; references from that code cannot be analysed by any parser

## Open questions
- Is a Java runtime acceptable for a developer/CI-only oracle (apex-ls JVM), and separately for an optional end-user 'deep mode', or must the shipped tool stay Node-only?
- Which real org is used for the trial, and can the fixture be deployed to a scratch org or Developer Edition so SymbolTable can serve as ground truth for it?
- Are the proposed bars (95% recall, 98% precision, 99% read/write accuracy on the labelled fixture) the right acceptance thresholds?
- Should dynamic references with unknown object be shown as low-confidence results or omitted from impact answers by default?
- Is a 4-day time-box (hard stop 5) acceptable for the trial inside Phase 0?
- Could not verify: whether Tooling SymbolTable.externalReferences lists sObject fields with positions, when its references arrays are empty, and the row limits of MetadataComponentDependency
- Could not verify: installs of apex-parser and web-tree-sitter-sfapex on macOS and Windows, and the minimum Java version apex-ls 6.4.0 supports

- [hands-on] (C) JVM apex-ls 6.4.0: what the dependency API returns
  EVIDENCE: DependencyReport JSON is class-level: {"name":"InvoiceService","dependencies":["AccountHelper","Schema.Invoice__c","Schema.Account"]}. - [hands-on] (C) JVM apex-ls resolves expression types internally and exposes that only through position queries
  EVIDENCE: Org.getDefinition(path,line,col,content) returned the field-meta.xml for custom fields in expressions, including inv.Account__r.Tier__c (relationship hop), an aliased loop variable, Map<Id,Account>.get(k).Risk_Score__c, an SObjectField token, and inside a syntax-broken class.
