# salesforce-libs

## Summary
Both libraries are usable from a plain Node CLI with no sf binary installed: @salesforce/core 9.4.6 and @salesforce/source-deploy-retrieve (SDR) 13.12.0 are Apache-2.0, CommonJS, require Node >=22, and together install 241 packages / 80 MB with no native modules or install scripts. I verified against local mock Salesforce servers (no real org was available) that an existing CLI-style login is read by alias via StateAggregator/AuthInfo/Org/Connection, that Tooling queries go through conn.tooling.query, and that a full SDR retrieve (wildcard ComponentSet -> retrieve -> poll -> decomposed source format on disk) and resume-by-job-id work. The biggest trap is auth persistence: AuthInfo's built-in JWT flow writes an encrypted auth file to ~/.sfdx even if save() is never called, and a second run with the same username then throws AuthInfoOverwriteError; a verified non-persisting recipe exists (do the JWT exchange ourselves, pass accessTokenOptions with every field pre-seeded including instanceApiVersion). SDR's registry (542 types, 36 child types) and local resolver handle 11,300 components in under a second, but SDR silently skips Apex classes/triggers that lack a -meta.xml, and ComponentSet.fromConnection silently turns listMetadata errors into empty results, so the tool should own its inventory step. Current docs (API v68.0, Winter '27) state retrieve limits of 10,000 files, 39 MB zip and 600 MB unzipped (not the 400 MB older docs gave); a synthetic 31 MB / 9,001-file chunk took 5.7 s and 437 MB peak RSS to land in source format. MetadataComponentDependency is still Beta ("for evaluation purposes only, not for production use"), capped at 2,000 rows per Tooling query with no queryMore/OFFSET/ORDER BY, and SourceMember is documented as "Reserved for internal use" and unavailable in production, so listMetadata lastModifiedDate plus content hashes is the only portable change signal. Cold import of both libraries costs roughly 0.45-0.7 s and 118 MB RSS, and the libraries write to ~/.sfdx and ~/.sf as a side effect of merely connecting. Nothing was verified on macOS or Windows, against a real org, or against a login written by the real sf CLI.

## Recommendation
Adopt @salesforce/core ^9.4.6 and @salesforce/source-deploy-retrieve ^13.12.0, set the project's engines to Node >=22, and wrap both behind one small connectivity module so nothing else imports them (lazy-load it so commands that need no org skip the ~0.5 s import).

Auth: support two modes declared per source in orglens.toml. (1) cli-login, the default: resolve alias -> username with StateAggregator, then AuthInfo.create({username}) and Connection.create; accept that core refreshes tokens and writes them back to the user's auth file, since that is shared, expected CLI behaviour. (2) jwt-env for CI: define the tool's own env var names, do the JWT bearer exchange in our own code, and build the AuthInfo from accessTokenOptions with every field pre-seeded (username, orgId, isDevHub, namespacePrefix, instanceApiVersion, instanceApiVersionLastRetrieved) and a pinned connection version. Do not use AuthInfo's built-in JWT path: it persists an auth file and breaks on the second run. Set SF_DISABLE_LOG_FILE=true at process start unless the user set it, and write a decision record listing the files the libraries touch under ~/.sfdx and ~/.sf.

Retrieve: do not use ComponentSet.fromConnection. Build our own inventory with describeMetadata plus one listMetadata call per type (and per folder, and per child type), with bounded concurrency, storing full FileProperties (id, lastModifiedDate, manageableState, namespacePrefix) in the snapshot and recording any per-type failure as a failure. Plan chunks from that inventory using explicit member names, never wildcards, with standard objects named explicitly; budget each chunk well under the documented 10,000 files / 39 MB (start at about 3,000 files, and bisect and retry a chunk that fails on a limit). Retrieve each chunk through SDR with format 'source' so org and repo share one on-disk shape and one parser path, journal the job id and state per chunk in SQLite so an interrupted run resumes with new MetadataApiRetrieve({id}), and always set apiVersion/sourceApiVersion explicitly. Decide in a short spike whether to also keep the raw zip per chunk as immutable evidence.

Incremental refresh: design the inventory table now so a later phase can diff id + lastModifiedDate between snapshots and confirm with content hashes; treat SourceMember as out of scope for production orgs.

Cross-checks: use conn.tooling.query for ApexClass SymbolTable and for MetadataComponentDependency, treat both as advisory, partition Dependency API queries by type, and flag any query that returns exactly 2,000 rows as truncated instead of accepting it. Give the fixture project a -meta.xml for every class and trigger, and add a test that fails when a .cls or .trigger file on disk is not represented in the resolved ComponentSet.

## Risks
- Nothing here was run against a real Salesforce org or a login written by the real sf CLI; all org-facing behaviour was verified against local mock servers or read from source and docs.
- macOS and Windows were not tested: keychain access (macOS security tool, Windows key.json), path handling in SDR output, and import time under antivirus are unknown.
- The libraries write to the user's ~/.sfdx and ~/.sf (log file, alias.json, key.json, refreshed tokens, cached API version). A bug in our auth handling could overwrite a person's real CLI login; the accessTokenOptions-without-top-level-username path bypasses core's overwrite guard.
- Core's refresh-token rotation lock only protects against other processes running a core version that has the lock; a tool bundling an older or newer core than the user's CLI can double-rotate a refresh token and invalidate the login (stated in core's own source comments).
- CI access-token mode has no automatic refresh; a retrieve longer than the org's session timeout fails unless we re-mint the token.
- SDR skips content files without -meta.xml and swallows listMetadata errors without raising; any completeness claim needs our own checks.
- Each retrieve chunk is held fully in memory as base64 plus buffer plus unzipped content (437 MB peak for a 31 MB zip); several chunks in parallel can exhaust memory on small CI runners.
- The 10,000-file and 39 MB limits apply to files and compressed size, which the inventory can only estimate; chunks can still fail and need bisecting. Docs say limits can change without notice.
- MetadataComponentDependency is Beta, documented as not for production use, capped at 2,000 rows with no pagination, and has no published type coverage; it cannot be relied on as a complete cross-check on a 10,000-component org.
- ApexClass.SymbolTable is documented as containing no references and can be null, so it cannot validate field-level edges on its own.
- listMetadata lastModifiedDate is the only portable change signal for production orgs and its reliability per type is unverified; some changes may only be detectable by content hash after a full retrieve.
- Profile and PermissionSet content depends on what else is in the same retrieve, so chunking changes what comes back; naive chunking yields incomplete permission data.
- Both packages require Node >=22 and release very frequently (both were republished within the last two days); major-version churn and transitive advisories (currently 5 high via proxy-agent -> basic-ftp) are an ongoing maintenance cost for a single developer.
- The packages are CommonJS with about 1,240 modules loaded; bundling into a single file for the later desktop build may need the messageTransformer step the core README describes, which was not tried.
- JWT-format access tokens require API 68.0+ for SOAP metadata calls according to SDR's own warning; pinning an older API version could produce empty listings on such orgs.

## Open questions
- Which real org will be used for the first retrieve (production, sandbox type, or Developer Edition), and is there an existing sf CLI login for it on the machine where Phase 0 runs?
- Is it acceptable that the tool creates or updates files under ~/.sfdx and ~/.sf (shared with the Salesforce CLI), or must it leave the home directory untouched in CI mode even at the cost of redirecting HOME?
- For CI, will the JWT private key be supplied as a file path or as key content in a secret env var? Core needs a path; content means we handle the key ourselves.
- Should managed-package components be in scope for snapshots? Wildcard retrieves exclude them and explicit retrieval is harder.
- Should each snapshot keep the raw retrieve zips as evidence, or only the converted source-format files? This affects snapshot size and reproducibility.
- Is the Dependency API acceptable as a cross-check given Salesforce labels it Beta and 'not for production use'?
- Not verified: how long Salesforce keeps a completed retrieve job's result available for resume by job id.
- Not verified: the Tooling Bulk API 2.0 endpoint for MetadataComponentDependency and whether it works on the target org.
- Not verified: which metadata types reject wildcards or return unreliable lastModifiedDate; this needs the real org or per-type reference pages.
- Not verified: behaviour on Node 24, on macOS and on Windows.
