# sqlite-store

## Summary
Both node:sqlite and better-sqlite3 13.1.1 are viable for the single-file snapshot store, and on the same SQLite version (3.54.1) they gave identical file sizes and near-identical speed (within about 10 percent) in a 147k-component / 587k-reference benchmark on Node 22, 24 and 26; all testing was Linux x64 only. On 2026-11-11 Node 26 is Active LTS, Node 24 and 22 are Maintenance LTS (22 ends 2027-04-30), there is no Current line (27 is alpha), and @salesforce/core 9.4.6, source-deploy-retrieve 13.12.0 and @salesforce/cli all require Node >=22.0.0. I recommend a floor of Node 24.15 with node:sqlite as the default driver behind a thin driver port, and better-sqlite3 13.x as the tested fallback. node:sqlite is Release Candidate (stability 1.2, no warning) on 24.15+ and 26, but only 'Active development' with an ExperimentalWarning on 22, and Node 22.14.0's build has no FTS5. better-sqlite3 13 is now N-API with eight prebuilt binaries inside the npm tarball and no install script; it segfaults on Node 22.12 (N-API 9) and its Linux prebuild needs glibc 2.34. Schema design matters far more than driver choice: text keys in reference rows cost 322 MB per snapshot against 107 MB with integer ids, and full copies per snapshot reach 1,103 MB for 10 snapshots against 159 MB when unchanged component versions and their references are shared. For bodies, 150 MB of source over 10 snapshots at 2 percent churn is about 1.55 GB as raw full copies, 189 MB content-addressed, and 41-43 MB content-addressed with per-blob deflate or zstd. A recursive-CTE inbound traversal to depth 5 takes 0.01-0.09 ms from a leaf but 500-820 ms from a hub with 22k inbound references; loading adjacency into typed arrays costs 150-440 ms once and then answers the same hub query in about 3 ms. WAL with busy_timeout and BEGIN IMMEDIATE behaved correctly with a writer and a reader in separate processes, and user_version migrations with transactional DDL rolled back cleanly on both drivers. Never open the same file through both drivers in one process: in that setup a checkpoint ran past an active reader.

## Recommendation
Set the Node floor at 24 (engines ">=24.15.0"), develop on 26, and run CI on Node 24 and 26 across Linux, macOS and Windows. Node 22 reaches end of life on 2027-04-30, and on 22 node:sqlite is still experimental and prints a warning. If the owner wants Node 22 support, the floor becomes 22.14.0 and better-sqlite3 becomes mandatory.

Use node:sqlite as the default driver, behind a small driver port (open, exec, prepare/run/get/all/iterate, transaction, close). Keep a better-sqlite3 13.x adapter, pinned to an exact version, passing the same store test suite in one CI job as the fallback. The choice is low-stakes: both produce the same file and the same speed, so switching is an adapter swap. Switch to better-sqlite3 if node:sqlite breaks before going Stable, if Node 22 must be supported, if shared-SQLite Node builds cause bug reports, or if the desktop shell lacks node:sqlite. Never load both drivers against the same file in one process.

Use only the portable SQL subset in the port: plain ? or named parameters (no ?1), no boolean or undefined binds, blobs treated as Uint8Array.

Open sequence, taken from the old Python store:
1. Set busy_timeout (5000 ms) first.
2. Read PRAGMA user_version and application_id; refuse a newer file before any write.
3. Only then set journal_mode=WAL and synchronous=NORMAL, and run numbered migrations, each in BEGIN IMMEDIATE with the version bump inside the transaction.
4. Opening an up-to-date file performs no writes; diagnostics use a read-only connection.

At start-up, check the Node version before importing anything, then probe SQLite version, FTS5 with the trigram tokenizer, and that WAL actually engaged; report all of it in a doctor command.

Concurrency rules: every write transaction starts with BEGIN IMMEDIATE; one writer at a time (a second waits on busy_timeout, then gets a clear "another ingest is running" error); the web server uses short read transactions so checkpoints can complete; run wal_checkpoint(TRUNCATE) after each snapshot commit; document that the workspace must be on a local disk.

Schema direction, to record as a decision now and build in the ingest phase:
- Integer surrogate ids everywhere; text keys only in one identity table. STRICT tables; enum-like and confidence values as INTEGER.
- Shared-version layout: node (identity) / version (content hash, attributes) / snapshot_item (membership) / reference (source version to destination node, kind, origin, confidence, line) / blob (sha256, deflate-compressed body). Snapshots are immutable; pruning deletes membership rows and then orphans.
- Version identity must cover the extracted reference set, not just the file body, because Apex resolution can depend on other files; version at file granularity so line numbers stay valid.
- One trigram FTS5 index over distinct names, not one per snapshot.

Traversal: put it behind a graph-reader interface. Use SQL for direct lookups and listings; for multi-hop impact use an in-memory adjacency (typed arrays) when the process is long-lived or the start node is a hub, since the recursive CTE costs 0.5-0.8 s on hubs and both drivers are synchronous and would block a web server's event loop.

Phase 0 itself only needs the driver port, the open/migrate/doctor code, a minimal v1 schema (snapshot, source, blob, retrieved-file listing for the first retrieve), the cross-OS store smoke tests, and the two decision records with these numbers. Commit the benchmark harness to the repo so later schema changes can be re-measured.

## Risks
- node:sqlite is Release Candidate, not Stable, on Node 24 and 26; its API can still change. Mitigation is the driver port and the tested better-sqlite3 adapter.
- With node:sqlite the SQLite build is whatever the user's Node carries: Homebrew Node links Homebrew's SQLite, and the bundled version moves with Node patch releases. Features or behaviour could differ on some installs; the start-up probe catches missing FTS5 but not subtle differences.
- better-sqlite3 13.x is a four-month-old rewrite onto N-API and 13.1.1 was published the day of this research; pin an exact version and avoid adopting same-day releases. It segfaults rather than erroring on Node below 22.14.
- better-sqlite3's Linux prebuild needs glibc 2.34; older enterprise distros would need a compiler toolchain. Its Windows and macOS prebuilds were not exercised here.
- All measurements are Linux x64 with a warm page cache on a 4-core VM; Windows (antivirus, slower fsync) and macOS numbers are unknown until CI runs the smoke tests and benchmark there.
- The benchmark graph is synthetic. Real orgs may have far more edges if permission grants (profile and permission-set field access) are stored as references: 100 permission sets times 40,000 fields is millions of rows, several times the 600k tested.
- Both drivers are synchronous: a 0.5-0.8 s hub traversal in SQL would freeze a local web server's event loop unless traversal runs in memory or in a worker thread.
- The shared-version layout is only correct if a version's identity covers its extracted references; if references are keyed to the file hash alone, a change in another class can leave stale edges on an 'unchanged' component.
- A long-lived read transaction (for example a web request that streams slowly) blocks checkpoints and lets the WAL file grow without bound; a single large snapshot transaction already produced a 49-88 MB WAL.
- WAL does not work on network filesystems, and synced folders or cross-OS mounts are untested; a workspace placed there could fail or corrupt.
- The body-size estimate rests on a JavaScript/JSON corpus as a stand-in for Salesforce source; many tiny decomposed metadata files compress only about 2 times, so real compressed size could be 30-70 MB rather than 41-43 MB.
- A single FTS index spanning many snapshots slows common-term searches (2 ms to about 50 ms at 10 snapshots) and makes snapshot deletion slow (about 5 s); the per-snapshot full-copy layout carries both costs.

## Open questions
- Does Node 22 need to be supported? It reaches end of life on 2027-04-30 but is what the Salesforce packages and CLI still accept; supporting it forces better-sqlite3 as the driver and a third CI column.
- Is a native dependency acceptable as the fallback (27 MB unpacked, eight bundled binaries), or should the project stay strictly dependency-free for storage and accept the Release Candidate status of node:sqlite?
- Which desktop shell is intended later (Electron, Tauri, other)? It decides whether node:sqlite is even available there; this was not verified.
- Will profile and permission-set field access be stored as graph references? It changes the edge count by an order of magnitude and should be benchmarked before the schema is fixed.
- How many snapshots should be kept by default, and is pruning automatic? This sets whether the shared-version layout's extra complexity is needed from the first schema or can follow later.
- Should full source bodies be stored in the database at all, or only hashes plus the analysed facts, with bodies left on disk or in Git? Storing them costs roughly 40 MB compressed per 150 MB org and enables offline diff and re-analysis.
- Is a hub query time of 0.5-0.8 s acceptable for the first CLI release, or should in-memory traversal be built from the start?
- Unverified and worth a short check in Phase 0 CI: both drivers on Windows and macOS, Node packages from Linux distributions (shared SQLite or not), single-executable packaging, and the documented stability of node:zlib's zstd functions.

  EVIDENCE: alts/alt.cjs on Node 22.23.4: insert of 300k rows: better-sqlite3 591 ms, node:sqlite 790 ms, sql.js 872 ms, node-sqlite3-wasm 1,063 ms, libsql 1,585 ms, sqlite3 12,292 ms. sql.js: 'no such module: fts5'. node-sqlite3-wasm: PRAGMA journal_mode=WAL returned 'delete'. libsql optionalDependencies list 9 platform packages without win32-arm64. All MIT except sqlite3 (BSD-3-Clause). @sqlite.org/sqlite-wasm 3.54.1 exists (Apache-2.0, node >=22) but was not tested.
- [hands-on] Driver start-up cost is negligible for a CLI: require, open a 1.1 GB database read-only and run one query takes about 0.7 ms with node:sqlite and 9-11 ms with better-sqlite3.
  EVIDENCE: start-node.cjs and start-bs3.cjs, three runs each on Node 24.22.3, warm page cache.
- [hands-on] On-disk size can change with the driver or Node patch version for the same data: the reference table's payload was 22.5 MB under node:sqlite on Node 22.23.4 and 26.7 MB under node:sqlite on 22.23.5 and under better-sqlite3 (about 7 bytes per row).
  EVIDENCE: dbstat payload sums on two files built from identical input. The gap matches integral values in the REAL 'confidence' column being stored as 8-byte floats instead of zero-byte integers, but a micro-test binding the literal 1 did not reproduce it, so the exact mechanism is not established.
- [unverified] Whether node:sqlite is usable inside Electron's bundled Node, how either driver behaves in a Node single-executable build, and whether node:zlib's zstd functions are marked stable were not checked.
  EVIDENCE: zstdCompressSync exists and ran on 22.23.5, 24.22.3 and 26.13.1 without printing its own warning, but its documented stability was not read. No Electron or single-executable test was run.
