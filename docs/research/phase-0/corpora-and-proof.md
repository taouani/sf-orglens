# corpora-and-proof

## Summary
Corpora: I shallow-cloned and measured 19 public repos. NPSP is the only one that reaches the 10,000-component target in source format (11,715 components via SDR's resolver in 0.53 s, 1,044 Apex classes, 319k Apex lines), and it is rich in dynamic SOQL, field sets and custom-metadata field mappings, but it has zero flows and needs CumulusCI plus four dependency packages to deploy. Recommended standard corpora: apex-recipes (CC0, 139 classes, one-command scratch deploy) as the deployable ground-truth corpus, Nebula Logger (MIT, 236 classes, 10 flows, 100 custom-metadata records) as the mid-size deployable corpus, and NPSP (BSD-3) as the parse-only scale and dynamic-reference corpus; LightningFlowComponents (280 flows) is an optional parse-only flow corpus for later.

Free orgs: a Developer Edition org is free, allows 15,000 API calls per 24 hours and can be a Dev Hub with 3 active / 6 daily scratch orgs (max 30 days each). The new Developer Edition expires without regular login; a Salesforce employee stated 45 days. Creating connected apps is disabled by default since Spring '26, and since May 2026 the CLI redacts auth URLs and tokens from `sf org display`, so CI needs either JWT with an external client app (persistent org) or a stored SFDX auth URL (Dev Hub).

Ground truth: the Dependency API is still Beta at API v68.0, limited to 2,000 rows per Tooling query with no queryMore/ORDER BY/OFFSET and no name filters, 100,000 via Bulk API 2.0, and reports only via Bulk. `ApexClass.SymbolTable` is documented as containing no references; references need `ApexClassMember`. A real recorded unfiltered Dependency API response in an old repo returned 1,943 rows, 94% Layout->CustomField and zero Apex rows, so unfiltered queries are not a usable ground truth; queries must be partitioned.

Old fixtures: 72 small files across the three repos, with expected values only inside Python assertions (no JSON goldens), only one formula in metadata, and several files not resolvable by SDR as laid out. Not verified: I could not open the SymbolTable reference page or the Dependency API usage sub-pages, and I deployed nothing to any org, so what the Dependency API returns for Apex/Flow/formula field usage is unconfirmed and must be measured in Phase 0.

## Recommendation
1. STANDARD CORPORA (pin each by commit SHA in a corpora manifest; fetch on demand, never vendor):
- apex-recipes: deployable ground-truth corpus. Small, CC0, current API version, one-command scratch deploy. Use it for the Apex trial (parse success on 139 classes) and as the first non-fixture org for the Dependency API comparison.
- Nebula Logger: mid-size deployable corpus. Stresses custom-metadata-driven config, flows calling Apex, 817 fields, no namespace. Use from Phase 2 onward (flows, custom metadata).
- NPSP: parse-only scale and dynamic-reference corpus. Stresses 10,000+ component ingest, 319k lines of Apex, dynamic SOQL, field sets, field mappings held as strings, and namespace prefixes. Use repo ingest only in Phase 0; do not plan an NPSP org deploy in Phase 0.
- Optional later: LightningFlowComponents as a parse-only flow corpus (280 flows) when the flow parser lands; DLRS if a dense dynamic-SOQL sample is wanted.

2. ORGS: one persistent Developer Edition org holding the fixture project (JWT via an external client app, retrieve-only), with Dev Hub enabled on the same or a second Developer Edition org for scratch orgs used by apex-recipes/Nebula deploys and any SymbolTable compile cross-check. Store auth as CI secrets; run live-org jobs on a schedule and on demand, not on every pull request, so 3 active / 6 daily scratch orgs and 15,000 API calls are never the bottleneck. Add a scheduled keep-alive and treat org loss as recoverable: the fixture must be redeployable from the repo with one script.

4. ANSWER KEY: hand-written YAML (comments allowed), validated by a JSON Schema, one file per fixture version:
schemaVersion, fixture, apiVersion
scope: list of reference kinds that are exhaustively keyed (closed world for those kinds)
components: [{id: 'CustomField:Invoice__c.Total__c', type, file}]  (complete inventory)
references: [{id: 'R-0042', source: {component: 'ApexClass:InvoiceService', member: 'markPaid(Id)', file, line, column, match: 'inv.Status__c'}, target: 'CustomField:Invoice__c.Status__c', kind: field-read|field-write|object-ref|class-ref|method-call|formula-ref|rule-ref|rollup-ref|lookup-filter-ref, access: read|write|readwrite|none, via: soql-select|soql-where|assignment|dml|sobject-get|sobject-put|constructor|formula|error-display-field|..., tier: definite|resolved-dynamic|heuristic|unresolvable, phase: 1, dependencyApi: expected|not-expected|unknown, notes}]
negatives: [{id: 'N-0003', source: {file, line, match}, target, reason}]  (must never be reported)
A key lint test runs in CI: ids unique; every file exists; the text at file:line contains 'match'; every target and source is in components; components equals the set SDR resolves from the fixture.

5. CORRECTNESS GATE:
Gate A, fixture answer key (offline, every pull request). Compare at two levels: component level (source component, target component, access) and location level (file, line, target, access). TP = reported and in key; FN = in key with phase <= current phase and not reported; FP = reported, of a kind listed in scope, and not in key; any hit on a negative is an FP. Report precision and recall per tier, per kind and per phase. Pass: precision 1.0 and recall 1.0 for tier definite and resolved-dynamic at both levels; every 'unresolvable' entry is reported as an explicit unresolved-dynamic marker at the right line; zero negatives hit.
Gate B, Dependency API comparison (live org, scheduled). D = Dependency API edges, O = tool edges projected to component level (drop member, line and access). A missing dependency is an edge in D, of a type pair in scope for the current phase, whose normalised form is not in O and is not matched by an explained-difference entry. Pass: zero unexplained missing edges. Edges in O not in D are never failures; they are counted per kind as 'beyond Dependency API' and each must carry a tier and a source location.
Normalisation: (1) resolve by ID, not name: build ID maps from Tooling CustomField (Id, DeveloperName, NamespacePrefix, TableEnumOrId) and CustomObject (Id, DeveloperName, NamespacePrefix) to get Object.Field__c; TableEnumOrId is a standard object name or a custom object Id; (2) always 18-character IDs; (3) compare names case-insensitively, with namespace as ns__ prefix; (4) map Dependency API type names to Metadata API type names through a versioned table (StandardEntity -> standard object named by the ID field; flow rows collapsed to the flow API name; validation rules resolved through Tooling ValidationRule); an unmapped type fails the gate until classified; (5) drop structural self/parent edges on both sides; (6) set semantics to remove duplicates; (7) exclude sources whose body is hidden (managed Apex) with an explicit category.
Completeness guard: partition Dependency API queries by MetadataComponentType and RefMetadataComponentType (and by RefMetadataComponentId per field when needed); if any partition returns 2,000 rows, split further or switch to Bulk API 2.0; if any partition stays saturated the gate result is 'invalid', not 'pass'.
Explained differences: a reviewed file in the repo, entries {id, direction: dapi-only|tool-only, srcType, refType, name pattern, category: DAPI_STALE|DAPI_FALSE_POSITIVE|OUT_OF_SCOPE_TYPE|PHASE_NOT_YET|MANAGED_HIDDEN|TOOL_BUG_TRACKED, reason, evidence, issue, expires}. The gate fails on an expired entry, warns on an entry that matches nothing, and a release requires zero TOOL_BUG_TRACKED entries.
Store the raw Dependency API result for the fixture org as a committed JSON snapshot so the comparison also runs offline.

## Risks
- The Developer Edition org can expire after a period without login (45 days per a Salesforce employee's community reply); it is not confirmed that an API or JWT login counts as a login. Mitigation: fixture redeployable by script; keep-alive job; occasional interactive login.
- JWT for a Dev Hub that creates scratch orgs requires a connected app, and connected app creation is disabled by default since Spring '26; a free org may not be able to get it enabled. Fallback is a stored SFDX auth URL, which is a long-lived refresh token in a CI secret.
- The Dependency API is Beta with no availability guarantee and may change or be withdrawn; it also truncates silently at 2,000 rows per Tooling query. A gate built on it can pass on incomplete data unless the completeness guard is enforced.
- What the Dependency API returns for Apex, Flow and formula field usage is unverified; if it turns out to omit Apex-to-field edges, Gate B loses most of its value for the tool's main feature and the fixture answer key becomes the only proof.
- The SymbolTable cross-check may be weaker than assumed: ApexClass.SymbolTable has no references, the reference-bearing variant needs a compile through Tooling records, and externalReferences may not include sObject fields at all.
- A hand-written answer key drifts when fixture files are edited; without the lint test, line numbers go stale and produce false failures. Windows CRLF checkout would shift nothing in line count but can break match-text checks if not normalised.
- NPSP is on API 53.0 and has zero flows and three validation rules, so it does not exercise flow or validation-rule parsing; scale numbers from it are 55% translations. Passing on NPSP says little about a modern flow-heavy org.
- No free org can hold a real 10,000-component customer-like org with unmanaged NPSP-scale Apex in a simple way; scale against a live org (API paging, retrieve chunking, rate limits) will stay untested until a user's org is available.
- Corpus repos move: upstream changes alter counts and can break deploys; pin by SHA and re-pin deliberately.
- [A finding about data in one of the earlier private prototypes was removed from this public copy. Its consequence: no recorded API responses and no fixtures are copied from the prototypes.]
- Public sample repos carry different licences (CC0, MIT, BSD-3, Apache-2.0); vendoring any of them into an Apache-2.0 repo would need attribution files. Fetching on demand avoids this.

The auth URL is now obtained with 'sf org auth show-sfdx-auth-url --target-org X --json' and used in CI with 'sf org login sfdx-url --sfdx-url-file'. Logging in with an already stored auth URL is unchanged, and a maintainer said @salesforce/core AuthInfo is not affected.
  EVIDENCE: forcedotcom/cli issue 3560 and the SFDX Developer Guide auth URL page. The SF_TEMP_SHOW_SECRETS workaround was announced for removal in summer 2026. CLI versions before 2.136.x behave the old way.
