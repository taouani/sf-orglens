# OrgLens 0.1.0-next.2

The third pre-release of OrgLens, made at the close of Phase 2 of the
[plan](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/plans/re-architecture-plan.md). It adds more
types of an org to the impact answers: flows, element by element, workflow rules and their actions, record types,
field sets, records of custom metadata types, email templates, report types and quick actions. It also holds the
corrections that a snapshot of a large org with `0.1.0-next.1` showed to be needed. It is published on npm under the
tag `next`, and its two packages are also attached to this page. The links of these notes lead to the documents as
they were for this version.

## What it does

OrgLens reads a Salesforce org, a sandbox or a repository folder into a snapshot on your own machine, and answers
one kind of question from it: what refers to this component, or what does it refer to?

- `orglens snapshot <source>` reads the metadata of a source and stores the files. Of what it stores, it analyses
  objects, fields and validation rules, as before, and now also:
  - **flows**, each element and resource a component of its own (`Flow:<flow>#element:<name>`), with what it
    reads, writes, calls or starts. A process of the Process Builder is a flow. Of an org, the snapshot holds the
    active version of a flow, which it asks for by its number where the org hands out a newer draft, and says that
    the newer version is there and not analysed;
  - **workflow rules** with their field updates, email alerts, outbound messages and tasks;
  - **record types**, **field sets** and the **records of custom metadata types**;
  - **email templates**, **report types** and **quick actions**.
- `orglens impact <component>` takes a flow with its elements: an element that refers to the component brings its
  flow, and the answer goes on from the flow. An element can be asked about by the name of its flow and its own,
  such as `Invoice_After_Save.Update_Account`. A name alone that fits an object and something else, such as the
  file of the workflow rules of that object, means the object, and the answer names the others. An answer names
  the flows in it whose active version has a newer one beside it.
- **Components of a managed package** installed in an org are marked with their package and left out of an answer
  about what refers to a component, which counts them and walks on through them. `--packages` keeps them.
- An answer about what refers to a component names fewer types as not analysed: only those whose components can
  name something of the answer. Every answer counts a warning of the analysis only where it can bear on it. So more
  answers are complete.
- The cross-check with the Dependency API of Salesforce covers the new types, as far as Salesforce reports them.
  For the rows of flows, a snapshot asks the org for the ids of the versions of each flow through two more objects
  of the Tooling API, `FlowDefinition` and `Flow`, which describe metadata. The reading of the rows no longer takes
  an answer below the limit of the API as whole.
- An object refers to the page or component that overrides one of its actions. The page or component is named and
  not read. A snapshot of an org counts as retrieved a document, what belongs to person accounts, and a report or a
  dashboard in a folder inside a folder, when they come back under another name than the one the org lists them by.
- `coverage` shows the new types, the components of packages, and the new parts of the cross-check.
  [docs/cli.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/cli.md) describes the commands.

OrgLens reads metadata only. Its own code makes no request for a record, stores no credential, and sends nothing
anywhere but to the org it reads. Through the Tooling API it queries three objects, which say which component
refers to which and name the versions of each flow. One exception is not in its hands: when the session of a
Salesforce CLI login has expired, the library of Salesforce that renews it reads one row that describes the org
itself and looks for Dev Hub records, as the Salesforce CLI does.

## What it does not do

- **It does not analyse Apex**, Lightning components, Visualforce, layouts, Lightning pages, reports, permissions
  or the other types outside the ones above. A flow that calls an Apex action, or a quick action that opens a
  component, refers to it by name, and the class or component is not read. An impact answer about a field of an
  org with Apex says in its first lines that it is not complete, and names the types it does not cover. It never
  means "nothing else refers to this".
- Approval processes, assignment, escalation and auto-response rules, sharing rules, and duplicate and matching
  rules are not analysed. An answer names them as not analysed where they can refer to it.
- It does not run a flow, and does not say in which order the automation of an object runs.
- **In a snapshot of an org, the name of a flow alone does not find the flow.** The org lists a definition of every
  flow under the same name (`FlowDefinition`), so `orglens impact Invoice_After_Save` ends with the error
  `COMPONENT_AMBIGUOUS` and the exit code `2`. Name the flow with its type, `Flow:Invoice_After_Save`, as the hint of
  the error says. A name with an element, such as `Invoice_After_Save.Update_Account`, finds the element.
- A flow that writes a token of a build tool before its names, as the processes of the codebase PMM write
  `%%%NAMESPACE%%%`, gives warnings and no reference for those names.
- It does not compare two snapshots, does not say what a pull request affects, and does not judge what a specific
  change breaks. It answers by reachability only.
- It has no language-model feature and no user interface besides the command line.

## What is proven, and what is not

- The answer key of the fixture project, written by hand: 510 references, 184 of them in Apex, which this version
  does not read. Of the other 326, of which 214 are in the files of this phase, every entry that is not marked as a
  stretch is found, at its line, and nothing else is reported. No negative case is hit. The key was written before
  the analysers it scores, except the 19 entries of the report type and the quick action, which were written in the
  same pull request as their analysers.
- The test org, a Developer Edition org with the fixture project of 120 components deployed: of the 136 rows of
  the Dependency API that are compared, the analysis missed none. Salesforce reports 47 of the 49 pairs from a flow
  to a custom field, the custom fields a field update reads, the type of a record of a custom metadata type, the
  custom fields of a field set, the three custom fields of the email template and the object they are of, and of a
  quick action the object it creates records of and the field `targetParentField`. It reports nothing from a
  workflow rule itself, a record type, a report type, an email alert, an outbound message or a task. For those the
  key is the measure, and for workflow rules and record types also the check by hand below. The numbers are in the
  note [real-org.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/research/phase-2/real-org.md).
- Eight public codebases: every flow, 23 with 151 elements, every file of workflow rules and every record type in
  their package folders were read by hand against what OrgLens reports. Of 1,725 references none is wrong. Seven
  names are missed, all in flows, and OrgLens gives no warning for them: a flow of a package that one flow
  overrides, and six names of the object that a flow hands to a generic Apex action. The note names the cause of
  each. The field sets were held against their files by a script, and the 31 email templates, 8 report types and
  54 quick actions of the codebases were read without an error and not checked by hand. **No person has read an
  entry.** The first reader was the AI assistant that wrote the analysers, and the second an AI reviewer of the same
  kind. The numbers are in the note
  [public-codebases.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/research/phase-2/public-codebases.md).
- **Not verified:**
  - No command of this version ran against an org. A tool of the tests reads the test org through the engine, and
    no impact question was asked about a snapshot of an org.
  - The corrections from the snapshot of a large org with `0.1.0-next.1` were not run on that org or on any org
    of that size: the cross-check below the limit, the overrides of actions, person accounts, documents, folders
    inside folders, the lines of the report, and the components of managed packages. The test org has no package,
    no person accounts, no document and no folder inside a folder.
  - The forms of the Lightning and the Visualforce email templates, and the fields of the owner as a classic
    template writes them, were not seen on an org.
  - A flow with more than two versions on an org, and an org whose Tooling API does not name the versions of every
    flow, so the warning `FLOW_VERSIONS_NOT_READ` was not seen on an org.
  - An org with a namespace of its own, a sandbox, and an org with many flows.
  - That the new tries are enough when Windows refuses to create the lock of the configuration: the refusal cannot
    be forced on the machines of CI.
  - Memory was not measured. The times that were measured are of repositories on one Linux machine, not of an
    org: a made-up source of 100,072 components with 5,810 flows was read, stored and analysed in 11.6 to 12.2
    seconds, and an impact question on it took 0.15 to 0.19 seconds.

## What changed in names, JSON output and exit codes

No name of a command, an option, a package or an error code changed, and `schemaVersion` of the JSON output is
still `1`. No field was removed or changed its type. What changed:

- **New:** the option `--packages` of `impact`. New fields in the JSON output, among them `sameName`,
  `newerVersions`, `elementOf`, `package` and `packagesLeftOut` of `impact`, `packaged` of the types of a snapshot,
  `rowsOtherVersion` of the cross-check, and new issue codes and details. A program that reads the output ignores
  fields it does not know, as
  [docs/cli.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/cli.md#what-may-change-and-what-may-not)
  asks.
- **The configuration:** `exclude_types` in `orglens.toml` refuses the seven types that joined the logic tier,
  `EmailTemplate`, `ReportType`, `QuickAction`, `WorkflowAlert`, `WorkflowFieldUpdate`, `WorkflowOutboundMessage` and
  `WorkflowTask`. A workspace that names one of them ends every command with `CONFIG_INVALID` and the exit code `2`
  until the type is taken out of the list.
- **Fields that count differently:**
  - `notCovered.notAnalysed` of an answer about what refers to a component lists only the types whose components
    can name something of the answer, and `notCovered.analysisWarnings` counts only the warnings that can bear on
    the answer. It also counts the warning `FLOW_VERSION_UNKNOWN` of the reading of an org.
  - The nearer end of the reference of a result can be a component that is no result: an element of a flow for
    `--outgoing`, where the flow is the result, and a component of a package that was left out. A program that
    builds the chains from the results alone has to allow for both.
  - `parts` counts the elements of a flow and the parts of a file of workflow rules.
  - `crossCheck.state` is `whole` only where no answer shows that a row is missing, which is stricter than before.
    `requests` counts the queries for the versions of flows too, and an answer counts as near the limit from half
    of it. The rows of flows are compared, or counted in `rowsOtherVersion`, where they were counted as rows of a
    type that is not analysed.
  - Three issues of the reading of a flow name the flow in `component`, where every issue of the reading had
    `component: null`. A warning `NOT_RETRIEVED` of a component of a package says `details.tier: "logic"` where its
    type is of the logic tier, and does not make the snapshot partial.
- **Exit codes keep their meaning, and some commands end with another one than before:**
  - A snapshot of an org that lists a component of one of the seven types above and does not get it back is now
    `partial`, and `snapshot` ends with `5`. So does a snapshot where the active version of a flow does not come
    back (`ACTIVE_FLOW_NOT_RETRIEVED`): `0.1.0-next.1` kept the version the org handed out.
  - `impact` ends with `5` where something of a type this version analyses was not read, or its analysis had an
    error. Such a type was not analysed before, and the answer ended with `0`.
  - A pair that the Dependency API reports and the analysis lacks is the error `REFERENCE_MISSED`, so `snapshot`,
    `analyse` and every `impact` answer from that snapshot end with `5`. There are more such pairs to find: the rows
    of the new types, flows above all, the rows that the reading now gets where an answer below the limit was cut
    off, and the rows of components that came back under another name.
  - Some end with `0` where they ended with `5`. The Lightning page that overrides an action of an object, which the
    Dependency API reports, is now found. A record type of person accounts now counts as retrieved. A component of
    a managed package that the org lists and does not hand out is a warning, which does not make the snapshot
    partial.
  - `impact` with a name alone that fits an object and other components answers for the object, where it ended with
    `COMPONENT_AMBIGUOUS` and `2`. A name with one dot that fits a field and an element of a flow, where neither is
    an object, ends with `2`.

## When you have a workspace of an earlier version

This version migrates the database of a workspace to schema version 11, from 7, when a command writes to it, such as
`orglens analyse` or `orglens snapshot`. Until then `impact` and `coverage` end with `STORE_OUTDATED` and the exit
code `1`. An earlier version then refuses that database. A snapshot that an earlier version took is read as it is,
and is analysed for the new types once `orglens analyse` analyses it again. Until then an answer from it says that
these types are not analysed, and `coverage` shows its cross-check as one this version cannot read. A snapshot of an
org that was interrupted under an earlier version is not continued: `orglens snapshot` gives it up and begins a new
one. A snapshot of an org taken before this version holds no ids of the versions of its flows: `orglens analyse`
matches its rows from flows by the ids the org listed the flows with, and a new snapshot asks the org for the ids of
every version. It also does not keep the name a component came back under, so a component of a package that came
back under another name counts as the org's own there, until a new snapshot is taken.

## Install

Node.js 24.15 or newer is needed. One line installs the command line, and with it the engine:

```sh
npm install --global sf-orglens@0.1.0-next.2
```

`orglens --version` then prints a line that starts with `sf-orglens/0.1.0-next.2 engine/0.1.0-next.2`. The same
line moves an install of an earlier pre-release to this version.

The command line is the package `sf-orglens`, and the engine the package `@sf-orglens/engine`, which npm
installs with it. Both are published by a workflow of this repository, through the trusted publishing of npm,
with a provenance attestation that says which run built them (decision records
[0053](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/adr/0053-a-pre-release-is-published-on-npm.md)
and
[0054](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/adr/0054-a-pre-release-without-a-change-is-published.md)).
The same two files are attached to this page, with their checksums.

`npm install --global sf-orglens@next` installs the newest pre-release, and `npm update --global` moves an
install to it. While OrgLens has no release that is not a pre-release, npm gives the newest pre-release also to
an install without a tag.

The command is `orglens`, and the package is `sf-orglens`. **Do not run `npx orglens`:** on a machine without
OrgLens, npx fetches the package named `orglens` from the registry, and that name is not a package of this
project. To run OrgLens without installing it, use `npx sf-orglens@next`.

The packages bring the libraries of Salesforce they are built with. Their versions are fixed: this version has
`@salesforce/core` 9.5.0 and `@salesforce/source-deploy-retrieve` 13.13.0, where `0.1.0-next.1` had 9.4.6 and
13.12.0. The versions of what those libraries need in turn are chosen by npm at the moment of the install, and can
be newer than the ones the tests ran with.

To remove it: `npm uninstall --global sf-orglens`.

## What may still change

This is a pre-release. The names of the two packages and of the command, the JSON output and the exit codes can
change from one pre-release to the next. They are fixed with the first version of OrgLens on npm that is not a
pre-release (decision records
[0051](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/adr/0051-the-first-release-is-the-first-on-npm.md)
and
[0053](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/adr/0053-a-pre-release-is-published-on-npm.md)).

The changes of this version, pull request by pull request, are in the change logs of the two packages:
[sf-orglens](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/packages/cli/CHANGELOG.md) and
[@sf-orglens/engine](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/packages/engine/CHANGELOG.md).

Problems are reported as [issues](https://github.com/taouani/sf-orglens/issues). An issue must not contain data
of a real org: no names of components, no org id, no host name and no user name. A vulnerability is reported as
[SECURITY.md](https://github.com/taouani/sf-orglens/blob/main/SECURITY.md) says.
