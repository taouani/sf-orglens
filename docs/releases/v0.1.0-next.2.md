# OrgLens 0.1.0-next.2

The third pre-release of OrgLens, made at the close of Phase 2 of the
[plan](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/plans/re-architecture-plan.md). It adds the
declarative automation of an org to the impact answers: flows, element by element, workflow rules and their
actions, record types, field sets, records of custom metadata types, email templates, report types and quick
actions. It also holds the corrections that a snapshot of a large org with `0.1.0-next.1` showed to be needed. It
is published on npm under the tag `next`, and its two packages are also attached to this page. The links of these
notes lead to the documents as they were for this version.

## What it does

OrgLens reads a Salesforce org, a sandbox or a repository folder into a snapshot on your own machine, and answers
one kind of question from it: what refers to this component, or what does it refer to?

- `orglens snapshot <source>` reads the metadata of a source and stores the files. Of what it stores, it analyses
  objects, fields and validation rules, as before, and now also:
  - **flows**, each element and resource a component of its own (`Flow:<flow>#element:<name>`), with what it
    reads, writes, calls or starts. A process of the Process Builder is a flow. Of an org, the snapshot holds the
    active version of a flow, which it asks for by its number where the org hands out a newer draft, and says that
    the newer version is there and not analysed;
  - **workflow rules** with their field updates, email alerts, outbound messages and tasks;
  - **record types**, **field sets** and the **records of custom metadata types**;
  - **email templates**, **report types** and **quick actions**.
- `orglens impact <component>` takes a flow with its elements: an element that refers to the component brings its
  flow, and the answer goes on from the flow. An element can be asked about by the name of its flow and its own,
  such as `Invoice_After_Save.Update_Account`. A name alone that fits an object and something else, such as the
  file of the workflow rules of that object, means the object, and the answer names the others. An answer names
  the flows in it whose active version has a newer one beside it.
- **Components of a managed package** installed in an org are marked with their package and left out of an answer
  about what refers to a component, which counts them and walks on through them. `--packages` keeps them.
- An answer names fewer types as not analysed: only those whose components can name something of the answer. It
  counts a warning of the analysis only where it can bear on the answer. So more answers are complete.
- The cross-check with the Dependency API of Salesforce covers the new types, as far as Salesforce reports them.
  For the rows of flows, a snapshot asks the org for the ids of the versions of each flow through two more objects
  of the Tooling API, `FlowDefinition` and `Flow`, which describe metadata. The reading of the rows no longer takes
  an answer below the limit of the API as whole.
- A snapshot of an org reads the page or component that overrides an action of an object, and counts as retrieved
  a document, what belongs to person accounts, and a report or a dashboard in a folder inside a folder, when they
  come back under another name than the one the org lists them by.
- `coverage` shows the new types, the components of packages, and the new parts of the cross-check.
  [docs/cli.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/cli.md) describes the commands.

OrgLens reads metadata only. Its own code makes no request for a record, stores no credential, and sends nothing
anywhere but to the org it reads. Through the Tooling API it queries three objects, which say which component
refers to which and name the versions of each flow. One exception is not in its hands: when the session of a
Salesforce CLI login has expired, the library of Salesforce that renews it reads one row that describes the org
itself and looks for Dev Hub records, as the Salesforce CLI does.

## What it does not do

- **It does not analyse Apex**, Lightning components, Visualforce, layouts, Lightning pages, reports, permissions
  or the other types outside the ones above. A flow that calls an Apex action, or a quick action that opens a
  component, refers to it by name, and the class or component is not read. An impact answer about a field of an
  org with Apex says in its first lines that it is not complete, and names the types it does not cover. It never
  means "nothing else refers to this".
- Approval processes, assignment, escalation and auto-response rules, sharing rules, and duplicate and matching
  rules are not analysed. An answer names them as not analysed where they can refer to it.
- It does not run a flow, and does not say in which order the automation of an object runs.
- It does not compare two snapshots, does not say what a pull request affects, and does not judge what a specific
  change breaks. It answers by reachability only.
- It has no language-model feature and no user interface besides the command line.

## What is proven, and what is not

- The answer key of the fixture project, written by hand before the analysers: 510 references, of which 214 are in
  the files of this phase. Every entry that is not marked as a stretch is found, at its line, and nothing else is
  reported. No negative case is hit.
- The test org, a Developer Edition org with the fixture project of 120 components deployed: of the 136 rows of
  the Dependency API that are compared, the analysis missed none. Salesforce reports 47 of the 49 pairs from a flow
  to a custom field, the custom fields a field update reads, the type of a record of a custom metadata type, the
  custom fields of a field set, some custom fields of an email template with their object, and of a quick action
  the object it creates records of. It reports nothing from a workflow rule itself, a record type, a report type,
  an email alert, an outbound message or a task, so for those the key is the only measure. The numbers are in the note
  [real-org.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/research/phase-2/real-org.md).
- Eight public codebases: every flow, 23 with 151 elements, every file of workflow rules and every record type in
  their package folders were read by hand against what OrgLens reports. Of 1,725 references none is wrong. Seven
  names are missed, all in flows, and each is named with its cause: a flow of a package that one flow overrides,
  and six names of the object that a flow hands to a generic Apex action. **No person has read an entry.** The
  first reader was the AI assistant that wrote the analysers, and the second an AI reviewer of the same kind. The
  numbers are in the note
  [public-codebases.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/research/phase-2/public-codebases.md).
- **Not verified:**
  - The corrections from the snapshot of a large org with `0.1.0-next.1` were not run on that org or on any org
    of that size: the cross-check below the limit, the overrides of actions, person accounts, documents, folders
    inside folders, the lines of the report, and the components of managed packages. The test org has no package,
    no person accounts, no document and no folder inside a folder.
  - The forms of the Lightning and the Visualforce email templates were not seen on an org.
  - An org with a namespace of its own, a sandbox, and an org with many flows.
  - Memory was not measured. The times that were measured are of repositories on one Linux machine, not of an
    org: a made-up source of 100,072 components with 5,810 flows was read, stored and analysed in 11.6 to 12.2
    seconds, and an impact question on it took 0.15 to 0.19 seconds.

## What changed in names, JSON output and exit codes

No name of a command, an option, a package or an error code changed, and `schemaVersion` of the JSON output is
still `1`. What changed:

- **New fields** in the JSON output, among them `sameName`, `newerVersions`, `elementOf`, `package` and
  `packagesLeftOut` of `impact`, `packaged` of the types of a snapshot, `rowsOtherVersion` of the cross-check, and
  new issue codes and details. A program that reads the output ignores fields it does not know, as
  [docs/cli.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/cli.md#what-may-change-and-what-may-not)
  asks.
- **Fields that count differently:** `notCovered.analysisWarnings` counts only the warnings that can bear on the
  answer, and `notCovered.notAnalysed` lists only the types whose components can name something of the answer.
  `crossCheck.state` is `whole` only where no answer shows that a row is missing, which is stricter than before.
  Three issues of the reading of a flow name the flow in `component`, where every issue of the reading had
  `component: null`.
- **Exit codes keep their meaning, and some commands end with another one than before:**
  - A snapshot of an org that lists an email template, a report type, a quick action or an action of a workflow
    rule and does not get it back is now `partial`, and `snapshot` ends with `5`. These types are of the logic tier
    now.
  - A component of a managed package that the org lists and does not hand out is now a warning, which does not
    make the snapshot partial.
  - A pair that the Dependency API reports from one of the new types, a flow above all, and that the analysis
    lacks is the error `REFERENCE_MISSED`, so `snapshot` and every `impact` answer from that snapshot end with `5`.
  - `impact` with a name alone that fits an object and other components answers for the object with `0`, where
    it ended with `COMPONENT_AMBIGUOUS` and `2`. A name with one dot that fits a field and an element of a flow,
    where neither is an object, now ends with `2`.

## When you have a workspace of an earlier version

This version migrates the database of a workspace to schema version 11, from 7, when a command writes to it. An
earlier version then refuses that database. A snapshot that an earlier version took is read as it is, and is
analysed for the new types once `orglens analyse` analyses it again. Until then an answer from it says that
these types are not analysed. A snapshot of an org that was interrupted under an earlier version is not continued:
`orglens snapshot` gives it up and begins a new one. A snapshot of an org taken before this version holds no ids
of the versions of its flows: `orglens analyse` matches its rows from flows by the ids the org listed the flows
with, and a new snapshot asks the org for the ids of every version.

## Install

Node.js 24.15 or newer is needed. One line installs the command line, and with it the engine:

```sh
npm install --global sf-orglens@0.1.0-next.2
```

`orglens --version` then prints a line that starts with `sf-orglens/0.1.0-next.2 engine/0.1.0-next.2`. The same
line moves an install of an earlier pre-release to this version.

The command line is the package `sf-orglens`, and the engine the package `@sf-orglens/engine`, which npm
installs with it. Both are published by a workflow of this repository, through the trusted publishing of npm,
with a provenance attestation that says which run built them (decision records
[0053](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/adr/0053-a-pre-release-is-published-on-npm.md)
and
[0054](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/adr/0054-a-pre-release-without-a-change-is-published.md)).
The same two files are attached to this page, with their checksums.

`npm install --global sf-orglens@next` installs the newest pre-release, and `npm update --global` moves an
install to it. While OrgLens has no release that is not a pre-release, npm gives the newest pre-release also to
an install without a tag.

The command is `orglens`, and the package is `sf-orglens`. **Do not run `npx orglens`:** on a machine without
OrgLens, npx fetches the package named `orglens` from the registry, and that name is not a package of this
project. To run OrgLens without installing it, use `npx sf-orglens@next`.

The packages bring the libraries of Salesforce they are built with. Their versions are fixed. The versions of
what those libraries need in turn are chosen by npm at the moment of the install, and can be newer than the ones
the tests ran with.

To remove it: `npm uninstall --global sf-orglens`.

## What may still change

This is a pre-release. The names of the two packages and of the command, the JSON output and the exit codes can
change from one pre-release to the next. They are fixed with the first version of OrgLens on npm that is not a
pre-release (decision records
[0051](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/adr/0051-the-first-release-is-the-first-on-npm.md)
and
[0053](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/docs/adr/0053-a-pre-release-is-published-on-npm.md)).

The changes of this version, pull request by pull request, are in the change logs of the two packages:
[sf-orglens](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/packages/cli/CHANGELOG.md) and
[@sf-orglens/engine](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.2/packages/engine/CHANGELOG.md).

Problems are reported as [issues](https://github.com/taouani/sf-orglens/issues). An issue must not contain data
of a real org: no names of components, no org id, no host name and no user name. A vulnerability is reported as
[SECURITY.md](https://github.com/taouani/sf-orglens/blob/main/SECURITY.md) says.
