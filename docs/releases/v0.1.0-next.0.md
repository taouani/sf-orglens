# OrgLens 0.1.0-next.0

The first pre-release of OrgLens, made at the close of Phase 1 of the
[plan](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.0/docs/plans/re-architecture-plan.md).
It is for people who want to try the first slice on a repository or an org they know. It is on GitHub only:
nothing is published to npm. The links of these notes lead to the documents as they were for this version.

## What it does

OrgLens reads a Salesforce org, a sandbox or a repository folder into a snapshot on your own machine, and answers
one kind of question from it: what refers to this component?

- `orglens snapshot <source>` reads the metadata of a source and stores the files. Of what it stores, it analyses
  **objects, fields and validation rules**: the names in their formulas, and the lookups, roll-up summaries,
  lookup filters, default values and field dependencies written in their XML. Every reference has its kind, its
  confidence and the file and line it stands on.
- `orglens impact <component>` shows what refers to a field or an object, directly and through other fields and
  rules, with the reference each result is found by.
- `orglens coverage <source>` shows per metadata type what the snapshot holds, what was analysed, what could not
  be resolved, and what went wrong.
- A snapshot of an org or a sandbox is also held against the Dependency API of Salesforce, as a second opinion.
  A reference that Salesforce reports and the analysis did not find is an error that `coverage` names.
- Every command has a `--json` output.
  [docs/cli.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.0/docs/cli.md) describes the commands, and
  [docs/configuration.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.0/docs/configuration.md) the files of
  a workspace.

OrgLens reads metadata only. Its own code makes no request for a record, stores no credential, and sends nothing
anywhere but to the org it reads. One exception is not in its hands: when the session of a Salesforce CLI login
has expired, the library of Salesforce that renews it reads one row that describes the org itself and looks for
Dev Hub records, as the Salesforce CLI does.

## What it does not do

- **It does not analyse Apex, flows, workflow rules, record types, custom metadata, layouts, permissions or any
  other type.** A snapshot stores them. An impact answer says in its first lines that it is not complete and how
  many types are not analysed, and lists those types below its results. In an org with Apex and flows, an answer
  of this version to "what refers to this field" is therefore not complete, and it says so. It never means
  "nothing else refers to this".
- It does not compare two snapshots, does not say what a pull request affects, and does not judge what a specific
  change breaks. It answers by reachability only.
- It has no language-model feature and no user interface besides the command line.

## What is proven, and what is not

- The answer key of the fixture project of this repository, written by hand before the analyser: the 106
  references it holds for fields and validation rules are found, each at its line, and no other.
- Four public codebases: 368 formula fields, default values, validation rules, lookup filters and roll-up
  summaries were held against the 616 references OrgLens reports for them. The 133 that can hold a name were
  read one by one, and the 235 default values that are a literal as a list. None of the references is wrong.
  Four are missed, all in one formula, behind a lookup of another package that the codebase does not describe,
  and a warning names each. **No person has read an entry.** The first reader was the AI assistant that wrote
  the analyser, and the second an AI reviewer of the same kind that read the 133 again. The numbers are in the
  note
  [public-codebases.md](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.0/docs/research/phase-1/public-codebases.md).
- One real org, a Developer Edition org with the fixture project deployed: of the 56 pairs the Dependency API
  reports from a custom field or a validation rule, the analysis missed none.
- **Not verified:**
  - The commands `orglens snapshot`, `coverage` and `impact` have never been run against a real org. The one
    real org was read by the engine, started by a tool of the tests with a login by key. The commands are
    tested against a mock org.
  - A login of the Salesforce CLI on a person's machine, an org with thousands of components, a sandbox, and an
    org with a namespace.
  - On the one real org, a snapshot ends as `partial`, because Salesforce does not hand out six components that
    the org lists. On an org like that, `snapshot` and every `impact` answer end with the exit code 5.
  - Memory was not measured. The times that were measured are of repositories on one Linux machine, not of an
    org.

## Install

Node.js 24.15 or newer is needed. One line installs both packages, the engine and the command line:

```sh
npm install --global --allow-remote=root https://github.com/taouani/sf-orglens/releases/download/v0.1.0-next.0/sf-orglens-engine-0.1.0-next.0.tgz https://github.com/taouani/sf-orglens/releases/download/v0.1.0-next.0/sf-orglens-0.1.0-next.0.tgz
```

`orglens --version` then prints a line that starts with `sf-orglens/0.1.0-next.0 engine/0.1.0-next.0`.

`--allow-remote=root` is needed from npm 12 on, which installs from an address only when it is told to. By the
documentation of npm, it allows the addresses the line itself names and no other. npm 11 installs with the
option as well. The line was tried on Linux with npm 11.0, 11.19 and 12.2, with the two files served from an
address on the machine of the build. Before it publishes, the workflow tries it the same way on Linux, Windows
and macOS, with the npm that Node.js brings and with the newest one.

Give both addresses in the one line. The command line needs the engine package by its name, and this project
has published nothing under that name on npm. With the second address alone, npm asks the public registry for
the engine, and what it would find there is not from this project.

**Do not run `npm update --global` or `npm outdated --global` while OrgLens is installed this way.** npm does
not remember the addresses of a global install. Both commands ask the public registry for the two names, and
`npm update --global` puts whatever it finds there in the place of OrgLens, without a warning. To move to a
newer version, run the install line of that version.

The packages bring the libraries of Salesforce they are built with. Their versions are fixed. The versions of
what those libraries need in turn are chosen by npm at the moment of the install, and can be newer than the ones
the tests ran with.

To remove both: `npm uninstall --global sf-orglens @sf-orglens/engine`.

## First steps

With a repository in the Salesforce DX format, in a new folder next to it:

```sh
mkdir my-workspace
cd my-workspace
orglens init
orglens source add repo --kind git --repo ../my-repository
orglens snapshot repo
orglens coverage repo
orglens impact Account.My_Field__c
```

The repository is named by a path relative to the workspace. Nothing is written into it. A workspace can also be
the repository itself: `orglens init` there adds the file `orglens.toml` and the folder `.orglens`, which Git
ignores, and `orglens source add repo --kind git` declares it.

With an org, after a login with the Salesforce CLI (`sf org login web --alias my-org`):

```sh
orglens source add prod --kind org
orglens source link prod my-org
orglens source check prod
orglens snapshot prod
orglens impact --source prod Account.My_Field__c
```

A workspace with more than one source needs `--source` for every question, as in the last line. A snapshot of
an org takes minutes and says how far it is. `orglens doctor` checks that OrgLens can run.

## What may still change

This is a pre-release. The database of a workspace is migrated by a newer version, and an older version refuses
a database that a newer one wrote.

[open] Decision records 0022 and 0027 let the names of the packages and the JSON output change until the first
release. Whether this pre-release counts as that release is a question to the maintainer. This paragraph is
replaced by the answer before the version is published: the workflow refuses to publish notes that hold the
mark at its start.

The changes of this version, pull request by pull request, are in the change logs of the two packages:
[sf-orglens](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.0/packages/cli/CHANGELOG.md) and [@sf-orglens/engine](https://github.com/taouani/sf-orglens/blob/v0.1.0-next.0/packages/engine/CHANGELOG.md).

Problems are reported as [issues](https://github.com/taouani/sf-orglens/issues). An issue must not contain data
of a real org: no names of components, no org id, no host name and no user name. A vulnerability is reported as
[SECURITY.md](https://github.com/taouani/sf-orglens/blob/main/SECURITY.md) says.
